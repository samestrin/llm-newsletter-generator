# Changelog

## Unreleased

- Feeds are checked before a run. `POST /api/feeds/check` takes `{"url"}` and answers `{"ok", "title", "items", "error"}` after reading the address as a run reads a feed (robots.txt, the 10 MB cap, http and https only) and refusing a private or loopback address, the first one included; `error` is a plain sentence ("This address did not answer", "This is a web page, not a feed", "This feed has no items", "The site asks not to be read", and a few more). No model call and no model key; it needs the API token and takes 30 checks a minute from all callers together, past that 429 with `retry_after` and `Retry-After`. `POST /api/runs` checks every feed it names first: some fail and the run starts with the rest, listing the failed ones in its Fetching feeds step and in the report's failed sources; all fail is 422 with an `errors` list per feed. Feeds from `--config` are not checked. A run may ask for `per_feed`. A busy server's 409 now carries `{"detail", "retry_after"}` and a `Retry-After` header, declared in the spec. `NEWSLETTER_DEMO=1` turns on demo mode: a run takes at most 6 feeds (422 past that), reads at most 3 items per feed, and ignores `date`. `GET /api/presets` serves AI news, science and tech feed sets from `src/newsletter/api/presets.json`, with no token. (epic 08.1)
- `POST /api/runs` runs on the visitor's key or a demo code. With `X-Model-Preset` and `X-Model-Key` the run's model calls go only to that provider's base URL, with its models (from `providers.json`) and the visitor's key; with `X-Demo-Code` they go only to the demo gateway (`NEWSLETTER_DEMO_BASE_URL`, models from `NEWSLETTER_DEMO_<TIER>_MODEL`) with the code as the bearer, and without the gateway set the run is refused with 503. The key or code lives on that run only: it is in no run record, draft, report, response or log, and `Jobs` redacts it from that run's progress, error and draft on top of the server's secrets. A provider with no embedding model (Synthetic) still runs: no embedding call, every item its own story in feed order, and the Grouping and ranking stories step and the run report (`grouping_note`, shown as "Not grouped:") say "Synthetic has no embedding model: stories are not grouped by meaning"; that note alone does not make the report not ok. Without these headers a run uses the server's own key, unchanged. (epic 08.1)
- After Approve (still the sha256 of the text as read), the review page opens "Email preview": the approved draft as `GET /api/drafts/{id}/email` renders it, in an `iframe` with `sandbox=""` (no `allow-scripts`, nothing else allowed) and `srcdoc`, under "Nothing was sent. This is what would go out." There is no send button and no send code. If the preview cannot be read, the page shows the API's reason, the draft stays approved, and Try the preview again asks for it again; an edit that clears the approval hides the preview. (epic 09.1)
- The run report on the review page opens with a short summary built from the report: the models used (each once), the number of model calls and the total cost, with "some costs unknown" when `cost_complete` is false (or, on an older report, a step has no cost) and "unknown" when the report has no total. When the editor failed it shows the plain `editor_message` ("The editor failed." on an older report) instead of the raw error. The Model calls table, each step's cost and the editor's raw error are behind a Show details button, closed by default; what failed, was left out or kept neutral stays in view. (epic 09.1)
- A key or demo code the API refuses (401) no longer replaces the saved one: the panel says why, while storage, the page's client and the draft list keep the key that worked. A new key that meets any other failure is still kept, so Try again uses it. (epic 09)
- The live progress no longer treats a refused key as a lost connection. A 401 from `GET /api/runs/{id}` stops the polling at once and says "The server refused the key" with the API's message, so the key panel opens once instead of every 2 s after the visitor closes it; saving a key again resumes the run. Any other 4xx (but 404, 408 and 429) also stops it and says the server refused, with Try again and Start over. (epic 09)
- The review page shows a draft as a newsletter: its Markdown is drawn with `react-markdown` (headings, lead, themes, stories and claim links) instead of a block of plain text. HTML in the draft stays text (no `rehype-raw`: a hand-written parser would be a second place for an escaping bug), and a link is drawn only for an absolute http or https URL, opened in a new tab with `rel="noopener noreferrer"`; a relative URL, `javascript:`, `mailto:` or `data:` link is its text alone. Each flagged claim has a note beside it, by text and icon: the server's `explanation` (the model's `reason` on an older draft), the source `passage` and the source link; the Flags list shows the same. The run's `focus`, when the draft or its report carries one, is shown above the draft and in the run report. Edit opens the text box, Save stores the text with `PUT` and stays there, Done editing returns to the newsletter (off while an edit is unsaved; Discard changes drops it), and an approved draft warns that saving clears the approval. (epic 09)
- Each flagged claim explains itself, in code: a draft's `flags` and the run report's `flagged_claims` now carry the claim's `passage` and an `explanation` next to `source_url`. The new `newsletter.editor.explain` reads the numbers with the voice check's extractor: when a number of the claim is missing from its passage and the passage has a different number near the same words, it says "The article says 71; the draft said 95."; otherwise "The article does not say this." followed by the checking model's reason, marked as the model's, or "This claim could not be checked." Every figure in an explanation is in the claim or the passage, else the status is said alone. Drafts saved before still load, without the two fields. (epic 08)
- After Make my newsletter the page shows the run's live progress from `GET /api/runs/{id}`, asked every 2 s until the run is done or failed or the page leaves: Fetching feeds, Reading articles, Grouping and ranking stories, Writing claims, Checking claims against sources, Editing the issue and Done, each with its state in words and an icon (waiting, running, done, failed, skipped), its counts as a progress bar with text ("12 of 15 fetched", "story 3 of 8"), each failed feed with its reason on its own line, and how long a running step has run ("1 min 20 s"). A screen reader hears each step change; after 30 s with no change the page says "Still working on <step>…". When the run is done the page opens its draft; when it fails it shows the run's plain message and Start over; a failed poll shows "Lost contact, retrying…" and after 10 in a row it stops and says so, with Try again and Start over. The run's id alone is kept in session storage, so a reload resumes the progress once the key is back; it is cleared when the run is done, fails or is missing, or on Start over. (epic 09)
- With a key or demo code saved, the page opens on a form to make an issue instead of the draft list: one or two sentences on what the tool does, up to six feed rows (Add a feed, Remove; presets from `GET /api/presets` fill them as a shortcut), an optional focus of up to 300 characters sent as `focus`, Make my newsletter, and See an example, a link-style button that opens the seeded draft. Each row is checked with `POST /api/feeds/check` when the visitor leaves it and again before the run, showing "Checking…", then "OK, 20 items" or the API's plain reason next to the row, by text and icon in a live region; only the rows that pass are sent, and the button stays off until one does. A busy server (409) shows "Someone else is making one right now. Try again in a minute." with Try again, which opens after its `retry_after`. The drafts stay one click away as Earlier drafts (after the form on a phone); the run's id and the owner token the server issues are kept in session storage and the token is sent back as `X-Owner-Token`, so in demo mode the API lists the example and this browser's drafts. Server-key mode is unchanged. (epic 09)
- The review page has a key panel for servers that list providers at `GET /api/providers`: a provider list (Demo code, OpenAI, OpenRouter, Alibaba, Synthetic), a field labelled "Demo code" or "API key", "Remember on this device", Save, Clear and Close. It opens on the first visit and from a Key button in the header. The key or demo code is kept in session storage, or in local storage with Remember; Clear wipes both. It is sent only as the `X-Model-Preset` header with `X-Model-Key` or `X-Demo-Code`, and never put in a URL, a request body, a log line or the page. A provider with no embedding model says that stories will not be grouped by meaning. A 401 reopens the panel with the API's message, and a message that repeats the key is not shown. A server that answers no provider list (today's server, or one in server-key mode) gets the API token field as before, sent as `Authorization`. (epic 09)
- `GET /api/drafts/{id}/email` previews the approved draft as an HTML email: `{"html": ...}` in the same responsive shell as the issue's email, only after approval (409 with the reason before, and again after any edit until the new text is approved). The new `newsletter.render.render_email(markdown)` converts the draft's Markdown — including hand edits — with raw HTML escaped to text, links only for absolute http/https URLs (`safe_url`), and images shown as their alt text, so neither rendering nor opening the preview fetches anything. Nothing sends mail. (epic 08)
- Hacker News stories, hnrss entries and other link-only items (under 50 characters of their own text once the title, URLs and points and comments lines are taken out) get the linked article's main text as their passage, read with the web page source's timeout, 10 MB cap, redirect and robots.txt rules. `RunReport.linked_articles` lists each article read (`fetched`) and each one that could not be read (`skipped`, with why), in the Markdown and HTML run report and on the review page; a skipped item is never summarized from its title or metadata and makes the run not ok. A claim that states only a URL or a points, votes or comments count is dropped ("claim is only about the listing"), and the claims prompt asks for none. The README recommends `NEWSLETTER_TIMEOUT=300` for a reasoning model.
- The review page's Model calls table shows each step's Tokens in and Tokens out again: it read `input_tokens` and `output_tokens`, but the API sends `prompt_tokens` and `completion_tokens`. A contract test renders the seed sample's report as the API serves it (`web/src/contract/seed-report.json`, kept equal to the API's answer by `tests/test_web_contract.py`).

## 1.1.0 - 2026-11-17

The API documents itself, a review instance starts with a real draft, and this repo ships its half of the private review deploy.

- `newsletter serve` serves the OpenAPI spec at `GET /api/openapi.json` and a Scalar reference at `GET /api/docs` that reads it. The reference's script is vendored in `src/newsletter/api/static/scalar/` at Scalar's pinned version, its remote fonts, proxy and telemetry are off, and it draws in the app's accent colours in light and dark. Both pages are readable without the token; the spec declares every route and its error responses, and the bearer token as a security scheme so the reference's Test Request can send it. FastAPI's own docs pages and ReDoc stay off. (epic 07)
- `newsletter serve --seed-sample` writes the committed `open-models-week` eval replay — its text, flagged claims and run report — as one draft at start, once: a restart adds no second copy and an existing draft is never overwritten or re-approved. It needs no model key and no network. (epic 07)
- `docker-compose.embassy.yml` and `docs/deploy/embassy.md`: this repo's half of the private review deploy on embassy — `api` started with `serve --seed-sample` and `web` behind nginx, no host port, on the external `proxy` network, settings only from a host-only `.env.embassy` (now gitignored), no model key needed for the seeded draft. CI's `compose` job validates the file with a dummy `.env.embassy`, and `tests/test_embassy_compose.py` guards its shape. (epic 07)
- `npm run capture:live` (in `web/`, `LIVE_URL` set) records a session on a running instance — the drafts list, the seeded issue with a flagged claim and its citation, Approve, and `/api/docs` — into `docs/img/demo.gif`. Frames are 1280x800; a mixed size, another size, an empty recording or delays over 30 s are refused with the reason. The normal Playwright run skips `e2e/live/`. (epic 07)
- CI keeps the spec complete: `tests/test_spec_completeness.py` fails when a registered route (`include_in_schema=False` aside) is missing from the spec or has no response schema, and the `compose` job checks that through the web container `/api/openapi.json` answers JSON and `/api/docs` answers the Scalar page, not the review page's `index.html`. (epic 07)

## 1.0.0 - 2026-11-10

The first demo-ready release: sources from a config file, grouped and ranked stories, an editor pass with a faithfulness check, a human approval gate, a review page with light and dark mode, a one-command local start, and a static archive build.

- `docker compose up` starts with no environment set: `NEWSLETTER_API_TOKEN` defaults to `demo-token-change-me`, safe only because the page binds to `127.0.0.1`. The CI `compose` job runs without the token, and the README has a Try it section. (epic 06)
- The review page has one design token set with light and dark mode, a 360 px layout, a skip link, landmarks, focus rings and a flag icon for flagged claims; the browser test runs an axe check at desktop and 360 px in both color schemes. (epic 06)
- `newsletter archive --demo` takes `--markdown PATH` and `--html PATH` and writes them from the same draft that builds the site; `docs/sample/README.md` records the model, feeds and command of the one-off sample run. (epic 06)
- The README shows the review page in light and dark mode and at phone width (360 px), saved to `docs/img/` by the browser test, and links `docs/sample/`. (epic 06)
- The review page shows explicit empty, loading and error states: "Loading the drafts…" while the list loads, "No drafts yet" with a Refresh list button, and the API's reason when the list fails; "Loading the draft…" and "Loading the run report…" while a draft loads, its failure with Try again, "This draft has no text", "No run report was saved with this draft" (it used to say nothing failed) and "The run report could not be read" for a malformed report, while the rest of the draft still shows. Only the draft opened last fills the page when answers arrive out of order. (epic 06)
- The daily archive workflow (`.github/workflows/daily.yml`) is removed: no workflow runs on a schedule. `tests/test_daily.py` keeps the offline `archive --demo` build test with its argv in the test. (epic 06)
- `newsletter issue --config FILE` and `newsletter serve --config FILE` read the file's feeds, web pages (`- page: URL`) and Hacker News (`- hackernews: {min_score, limit}`), group copies of one story into one story with all its sources, and rank the stories closest to the file's `topic` first, with one `embedding` call. `newsletter issue` now needs `NEWSLETTER_EMBEDDING_MODEL` (exit 2 without it). The run report (`RunReport.left_out`, `RunReport.grouping_error`, and both the Markdown and HTML reports) lists every item that could not be grouped or was dropped, and a failed embedding call; either one makes the run exit 1. A `serve` run that names no feeds reads the file's sources. `newsletter archive` no longer takes `--config`. (epic 02)
- `newsletter.sources.HackerNewsSource(min_score=..., limit=...)` reads the front-page stories from the public Hacker News API, one item each, and filters out stories scoring under the threshold. It uses the shared fetcher (timeout, size cap, private-address redirect check) and lists a failed story list or story in the run report (epic 02).
- `newsletter.sources.PageSource` reads single article pages: it fetches each URL with the RSS source's fetcher and robots.txt check, keeps the page's main text (its `article`, else `main`, else the element with the most paragraph text) and title, and lists a page robots.txt forbids, a failed load or a page with no text as a failure instead of fetching or skipping it. Every fetch, feeds included, now stops at 10 MB (`MAX_BYTES`) and refuses a redirect to a host that resolves to a private, loopback or link-local address, checked on every hop.
- `newsletter.grouping.group_items(items, llm, topic=...)` groups near-duplicate items into one story with all their sources and ranks the stories closest to the topic first (ties keep input order), from one `embedding` model call. A failed or unusable embedding call sets `error` and keeps every item as its own story; every ungrouped or dropped item is listed in `left_out` for the run report. Not yet wired into `newsletter issue` or `serve` (epic 02 T5).
- `--config FILE` on `newsletter issue` and `newsletter archive` reads a YAML sources file (`topic`, `sources`, `limits.per_feed`), validated on load: an invalid file exits 2 with an error naming the file and the field. Feed URLs, `--topic` and `--per-feed` on the command line win over the file. `pyyaml` is now a runtime dependency. (epic 02)
- `newsletter issue --html FILE` also writes the edited issue as the HTML email: every claim linked to its source, flagged claims marked, and the run report with the cost per step.
- `newsletter.export` sends an approved issue to Buttondown (`POST /v1/emails` with `status: draft`), Beehiiv (`POST /v2/publications/{id}/posts` with `status: draft`) and Resend (`POST /broadcasts` with `send: false`, and no send call) as a draft only. Each connector is optional, set up from its key in the environment, with a timeout (`NEWSLETTER_EXPORT_TIMEOUT`, default 30s). Export is refused before any request unless a person's approval sha256 matches the current text. A failed call or a reply that is not a draft is reported as failed and never as exported, a connector with no draft-only endpoint is dropped and listed, and no key appears in a log or the report.
- `docs/case-study.md` is a case study of the project's accuracy design — claims quoting sources, per-claim checks, a human approval gate — built around the eval table from `evals/results.md` (5/5 planted false claims flagged, 100.0% reference coverage, $0.0100 per issue), with the replay caveat kept.
- The README says what the tool does, step by step, with screenshots of the review page and of an issue as the HTML email, and shows the eval table from `evals/results.md`. That file is now committed: a replay of recorded responses, labeled as one, until a live run replaces it. The browser test saves the screenshots to `docs/img/` from the `open-models-week` eval case, and `tests/test_readme.py` fails if the README's table, `evals/results.md` or the screenshot fixtures fall out of date.
- `newsletter issue` now runs the editor pass: claims quoting their source, a faithfulness check and a reasoning-model edit, written as Markdown. Every claim links to its source, unsupported or unchecked claims are marked, and the run report lists failed feeds, dropped and flagged claims, the writer's voice and the cost per step. It needs `NEWSLETTER_REASONING_MODEL` as well as the fast model, and `--topic` now belongs to `newsletter archive` only. With `YOURVOICE_API_KEY` set, the voice pass rewrites only the editor's prose (intro, themes, why it matters); claims, quotes, numbers and citation links pass through unchanged, and a failed voice call keeps the neutral prose and is listed in the run report.
- `docker compose up --build` runs the API and the review page: a `Dockerfile` with an `api` and a `web` (nginx) target, and a `docker-compose.yml` that publishes only the page on `127.0.0.1:8080` and forwards `/api` to the API. `NEWSLETTER_API_TOKEN` is required. CI gains a `compose` job that starts both and checks the page, the proxied health call and the token.
- `web/` is a review page (React and Vite) for the API's drafts: read the text with its flagged claims and run report, edit and save it (which clears the approval), and approve it with the sha256 of the text read. Draft text is shown as text, never as HTML, and only http and https sources are links. CI gains a `web` job that builds the page and runs its unit tests and a Playwright browser test of edit and approve against a fake API.
- `newsletter archive --demo --site DIR FEED_URL...` drafts an issue and builds the static archive in demo mode: the approval is an `automated-demo` record, valid for archive pages only and refused by `newsletter.archive.require_export`; every page carries an "Automated demo" label and every summary is marked unchecked. `--per-feed N` (on `issue` too) summarizes only the first N items of each feed.
- `newsletter serve` runs an HTTP API (FastAPI and uvicorn) that runs an issue as a background job with a status and a timeout: the feeds, then the editor pass, then the voice pass, then render. Each run leaves a draft, a JSON file in `NEWSLETTER_DATA_DIR` holding the text, flags and run report, that can be listed, edited and approved. Approval stores the sha256 of the draft text and any edit clears it. A run past `NEWSLETTER_RUN_TIMEOUT`, or cut off by a restart, ends as a reported error with no draft. It binds `127.0.0.1` by default. Every call except the health check needs the `NEWSLETTER_API_TOKEN`, and every write also needs a JSON body and an allowed `Origin`. No secret appears in a response, error body, stored file or log.
- `newsletter issue` writes the summaries in the writer's voice when `YOURVOICE_API_KEY` is set. It builds a yourvoice.dev profile from `NEWSLETTER_VOICE_SAMPLES` and caches it, then rewrites each summary with the reasoning model. A rewrite that drops, changes or adds a link, quoted string, number or claim id is rejected. A rejected rewrite, a failure or a timeout keeps the neutral summary and is listed in the run report. `newsletter.render.build_report` takes the voice pass too, so the Markdown and HTML run reports list it as well.
- `python -m newsletter.evals` prints an eval table (faithfulness rate, flag rate, planted false claims flagged, reference coverage, cost per issue) from two committed past feeds, each with a reference issue and recorded model responses that include planted false claims; it exits 1 if a planted claim is not flagged and runs in CI. `--live` runs the same feeds against real models (costs credit); `-o evals/results.md` saves the table.
- The shipped prompt templates are now protected by snapshot tests, and the retired `introduction.md` and `closing.md` prompts are gone (`item.md` is now `summary.md` until epic 03 T6 replaces the legacy writer).
- `newsletter.archive.build_site(issues, site_dir)` renders approved issues to a static site: an index and one page per issue at `issues/YYYY-MM-DD/index.html`. All feed and model text is HTML-escaped, only http and https links are rendered, the run report shows problems by feed host and count only, and the site is built in a temp dir and swapped in only when complete.
- A `v*` tag builds the `api` and `web` images from `Dockerfile` and pushes them to `ghcr.io/samestrin/llm-newsletter-generator/api` and `.../web`, tagged with the version (`1.2.3` and `1.2`). A pull request that changes the `Dockerfile` or the release workflow builds both without pushing.
- Rewrote `README.md` for the new package: install with `uv`, the `newsletter` CLI, and the `NEWSLETTER_*` environment settings; dropped the version badge.
- `newsletter issue FEED_URL...` drafts a plain issue: one fast-model summary and one link per feed item, credits each feed, and ends with a run report of failed feeds, dropped entries and model calls with their tokens and cost. It exits 1 when anything failed.
- The prompt templates moved from `prompts/` to `src/newsletter/prompts/` so they ship with the package.
